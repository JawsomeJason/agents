# Judge harness

Measures whether standards mined from a repo's review history help a reviewer that never sees the human comments catch what those humans flagged. It holds out a repo's newest reviewed changes, mines standards from the older ones with the `standards` skill, has fresh reviewers review each held-out diff with no standards, with shape A and with shape B, and grades their findings against the human comments.

The scripts hold only code. Pass every data path with `--data`, and keep data outside this repo, because review comments quote people and code. Each step caches its output under `--data`, so a rerun resumes where the last one stopped and repeats no paid call. The scripts use the Node standard library and the forge CLI (`gh`), plus `git`.

## Steps

Run from anywhere. `$D` is the data folder for one repo and `$S` is `plugins/standards/skills/standards`.

1. **Clone.** `git clone <repo url> $D/clone`.
2. **Split.** `node split.mjs --repo <owner/name> --clone $D/clone --data $D`. It runs the skill's `fetch-reviews.mjs` over a growing window of merged changes until it finds the 20 newest merged changes with at least 2 reviewer inline comments (not a bot, not the change's author), then keeps up to 400 changes merged before the oldest of those was opened. It writes `split.json` (the held-out changes, the reviewed commit of each, and the reviewer distribution of both sets), `mine/reviews.jsonl` and `heldout/reviews.jsonl`. A held-out change is graded on the reviewer inline comments made against the commit its first one points at, because later comments may describe code the reviewed diff never had.

   The held-out set is diversified, so one reviewer's taste is not the whole test. At most `--max-per-author` changes (default 2) come from one author, and at most `--max-per-series` (default 2) from one series. A series is changes by one author linked by either signal: a stacked base, where a change's base branch is another of that author's head branches rather than the default branch, or a shared title prefix before a part number, such as `Upload stack 3/8:` or `Retry (part 2)`. A snapshot `prs.json` from before branch names were recorded links by titles alone; delete it to re-list. When one reviewer wrote more than `--max-reviewer-share` (default 0.5) of the graded comments, split swaps out the change that reviewer dominates most for the newest older change they do not, growing the window as needed. It prints each reviewer's share, records it in `split.json` as `reviewers.heldout_share`, and warns when no window up to `--max-window` brings the top share under the limit.
3. **Mine.** Follow `$S/references/mine.md` from step 2, with `$D/mine/` in place of `.standards/`. Answer `questions.jsonl` with whatever answerer the environment offers.
4. **Agreement.** `node agree.mjs sample --questions $D/mine/questions.jsonl --out $D/agree/sample.jsonl`, have a second answerer answer the sample into `$D/agree/answers.jsonl`, then `node agree.mjs compare --sample $D/agree/sample.jsonl --first $D/mine/answers.jsonl --second $D/agree/answers.jsonl --out $D/agree/result.json`.
5. **Write.** Follow `$S/references/write.md` into `$D/standards-A/`, against a checkout of the repo at the last trunk commit before the cutoff, so the writer sees none of the held-out code. Record each area's slug and description in `$D/areas.json` as `[{"section": "§1", "slug": "...", "description": "..."}]`, then `node shape-b.mjs --a $D/standards-A/<skill> --areas $D/areas.json --out $D/standards-B --repo-slug <slug>`. Lint both with `node scripts/lint.mjs <dir>`.
6. **Label the held-out comments** the way mine does: `node $S/scripts/questions.mjs ask --reviews $D/heldout/reviews.jsonl --labels $D/mine/labels.json --out $D/heldout/questions.jsonl`, then answer it into `$D/heldout/answers.jsonl` with the same answerer as step 3.
7. **Stage.** `node stage.mjs --repo <owner/name> --clone $D/clone --data $D --workspace <dir> --standards-a $D/standards-A --standards-b $D/standards-B`. It fetches each held-out diff at its reviewed commit and builds one workspace per change and arm, with neutral names, for the arms `--arms` lists (default `none,A,B`; each standards arm needs its `--standards-` folder), and writes `review/manifest.json` and each prompt to `review/<arm>/<change>.prompt.md`. Every arm gets the same prompt, and the standards arms add one sentence pointing at the installed skills. The prompt asks for each problem the reviewer would raise, whatever its size. It no longer says to report only what the reviewer would post, because that line can read as an instruction to hold back nits, and a standards skill that asks for nits would then fight the harness rather than the baseline. Runs staged before this change used the older line, so compare arms only within one prompt version. A later version changed the standards arms' sentence: it asked the reviewer to follow the standards skill's `review` command, and reviewers took that as the whole job, raising mostly § findings and missing bugs an ordinary review caught. The standards arms now ask for an ordinary review first, kept whole, plus the standards pass on top. That makes three prompt versions: the original "only what you would post" line, the "whatever its size" line with review-only standards arms, and the ordinary review plus standards pass. Results from one version aren't comparable with another's, and runs staged under the earlier two are not re-run.
8. **Review.** For every workspace, spawn a fresh reviewer subagent with its `.prompt.md` as the whole prompt. Record each one's reported token use in `review/tokens.json` as `{"<workspace id>": tokens}`. Then `node grade.mjs collect --data $D`.
9. **Grade.** `node grade.mjs pairs --data $D` writes one yes/no question per finding and human comment on the same file within 10 lines, to `grade/pairs.questions.jsonl`. The default grader is two-grader consensus:
   1. Have a judgment model answer the pairs into `grade/pairs.answers.model.jsonl`, the way `mine` answers its questions file, and have a fresh subagent answer them into `grade/pairs.answers.subagent.jsonl`.
   2. Run `node grade.mjs consensus --data $D`. A pair where the two agree takes that verdict. The pairs where they differ go to `grade/pairs.tiebreak.questions.jsonl`, and it exits non-zero until a third grader, another fresh subagent, answers those into `grade/pairs.answers.tiebreak.jsonl`. Rerun it, and it writes `grade/pairs.answers.jsonl`, the consensus answers that `score` reads, and `grade/consensus.json`, with every pair's votes and the two graders' agreement rate. `--first`, `--second` and `--third` name other answer files.
   3. `node grade.mjs calibrate --data $D` samples 30 pairs into `grade/calibration.json`; label each `same_concern` by hand and rerun it for the consensus's agreement with the hand labels. Pass `--answers` to calibrate one grader's file on its own. `calibrate` writes `grade/calibration.result.json` for whichever file it was given, so copy it aside before calibrating another.
10. **Score.** `node grade.mjs score --data $D` writes `grade/metrics.json` and `grade/metrics.md`: convention recall, all-comment recall, false positives per change and mean tokens, per arm.

## Lens pass

`lens.mjs` tests whether a reviewer misses rules because it forgets to apply them. It asks one yes/no question for every pair of a § in a standards skill and an added hunk in a file that §'s Applies-to globs match, so every rule meets every hunk it covers. A § whose Applies to line says `by trigger` meets every hunk, and its question carries the Triggers line, so the answerer says no where the trigger does not match.

1. `node lens.mjs ask --standards $D/standards-A/<skill> --diffs $D/heldout/diffs --split $D/split.json --out $L/questions.jsonl` reads the diffs `stage.mjs` gave the reviewers. Each pair gets a `#violates` yes/no question, plus a `#line` choice of the added line that shows it and a `#heuristic` choice of the sign that fires. The three share the hunk as their state, so an answerer that groups by state reads each hunk once. A hunk that adds more than 40 lines is cut into pieces.
2. Answer the file with a judgment model, or with an agent. An agent may answer only the `#violates` questions.
3. `node lens.mjs collect --questions $L/questions.jsonl --answers <answers> --split $D/split.json --out $L/review/lens --threshold 0.5` writes one findings file per change. A yes becomes a finding at the chosen line, or at the hunk's first added line when no line was chosen, citing the §.
4. `node lens.mjs union --a $L/review/none --b $L/review/lens --split $D/split.json --out $L/review/union` models a free-form review followed by the lens pass.
5. Grade with `grade.mjs pairs --data $L --arms none,lens,union`, then the usual consensus and score. `--arms` names the folders under `review/` to grade, and `score` reads the same list from `pairs.meta.json`.

## What the numbers mean

- A human comment is a convention comment when its label is not `none`, the same rule `cluster.mjs` applies.
- A finding catches a human comment when the consensus says they raise the same concern: both graders, or the third grader when the first two disagree. A false positive is a finding that catches no human comment. Some false positives are real problems the humans missed, so the count is an upper bound on noise.
- An answer at exactly the threshold counts as its stated verdict, so an answerer's false at 0.5 is a no.
- Mean tokens is the reviewer's own reported token use per review, so it counts the diff and any source the reviewer read as well as the standards.
